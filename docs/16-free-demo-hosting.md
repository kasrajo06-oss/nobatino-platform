# نسخه نمایشی رایگان (بدون سرور و دامنه)

این سند توضیح می‌دهد چطور بدون خرید سرور و دامنه، سایت را برای همه قابل دیدن کنیم. دو بخش داریم:

| بخش | آدرس | چه چیزی نشان می‌دهد | هزینه |
|---|---|---|---|
| **صفحه معرفی** (GitHub Pages) | `https://kasrajo06-oss.github.io/nobatino-platform/` | معرفی، تصاویر، حساب‌های نمایشی، دکمه ورود به نسخه زنده | رایگان، همیشه روشن |
| **نسخه نمایشی زنده** (Render) | `https://nobatino-demo.onrender.com` | خود سایت با همه امکانات: جستجو، رزرو، پنل‌ها، چت و تماس تصویری | رایگان، بعد از ۱۵ دقیقه بی‌استفاده می‌خوابد |
| **یا: نسخه نمایشی روی Coolify** | `https://nobatino.SERVER_IP.sslip.io` | همان سایت، روی سرور خودتان | هزینه سرور؛ همیشه روشن |

## چرا GitHub Pages به‌تنهایی کافی نیست؟

GitHub Pages فقط فایل ثابت (HTML، CSS، JS، تصویر) میزبانی می‌کند. این سایت بک‌اند Django، پایگاه داده، ورود با کد، رزرو نوبت و تماس تصویری دارد که همه به یک سرور در حال اجرا نیاز دارند. پس:

- **GitHub Pages** صفحه معرفی را میزبانی می‌کند (پوشه [`site/`](../site) + تصاویر [`docs/images/`](images)).
- **Render** (یا هر سرویس رایگان دیگری که Docker اجرا کند) خود سایت را اجرا می‌کند.

## نسخه نمایشی در یک کانتینر

[`deploy/demo/Dockerfile`](../deploy/demo/Dockerfile) کل پلتفرم را در **یک کانتینر** می‌سازد تا روی پلن‌های رایگان (۵۱۲ مگابایت رم) جا شود:

```
بازدیدکننده ──https──► Next.js (پورت عمومی $PORT)
                         │  /api ، /media ، /admin ، /static
                         ▼
                       Django + gunicorn (127.0.0.1:8000) ──► SQLite (/data/demo.sqlite3)
                       رشته run_periodic داخل gunicorn (به‌جای Celery beat)
```

| موضوع | نسخه اصلی (`infra/docker-compose.prod.yml`) | نسخه نمایشی |
|---|---|---|
| پایگاه داده | PostgreSQL | SQLite داخل کانتینر |
| صف و کارهای زمان‌بندی | Redis + Celery worker/beat | اجرای مستقیم کارها + دستور `run_periodic` |
| فایل‌ها | MinIO + دیسک خصوصی | دیسک کانتینر |
| تنظیمات | `config.settings.prod` | `config.settings.demo` (همیشه `STAGING`) |
| ورود | پیامک واقعی | کد روی صفحه + دکمه حساب‌های نمایشی |
| پرداخت | زرین‌پال | پرداخت آزمایشی |
| موتورهای جستجو | ایندکس می‌شود | `noindex` |

داده‌های ساختگی (۱۵۰ پزشک، ۶۰ مرکز، نوبت‌ها، نظرات، مقالات) **هنگام ساخت image** ساخته می‌شوند، چون سرورهای رایگان کُند هستند. هر بار که سرویس دوباره راه بیفتد (بیدار شدن از خواب یا استقرار جدید)، داده‌ها به حالت اول برمی‌گردند. اجرای `run_periodic` در شروع کار نوبت‌های خالی روزهای آینده را دوباره می‌سازد.

اجرا روی کامپیوتر خودتان:

```bash
docker build -f deploy/demo/Dockerfile -t nobatino-demo .
docker run --rm -p 8080:8080 nobatino-demo
# http://localhost:8080
```

## مرحله ۱: راه‌اندازی نسخه زنده روی Render

1. به <https://render.com> بروید و با **Sign in with GitHub** وارد شوید (کارت بانکی لازم نیست).
2. **New → Blueprint** را بزنید و مخزن `nobatino-platform` را انتخاب کنید. Render فایل [`render.yaml`](../render.yaml) را می‌خواند و سرویس `nobatino-demo` را با پلن رایگان می‌سازد.
3. **Apply** را بزنید. اولین ساخت حدود ۱۰ دقیقه طول می‌کشد.
4. بعد از پایان، آدرس سرویس بالای صفحه نوشته شده است (معمولاً `https://nobatino-demo.onrender.com`).
   - اگر آدرس دیگری گرفتید، در Render ← سرویس ← **Environment** مقدار `NEXT_PUBLIC_SITE_URL` را به آدرس جدید تغییر دهید و **Manual Deploy** بزنید.
5. با هر push روی شاخه `main`، Render سایت را خودکار دوباره می‌سازد.

محدودیت‌های پلن رایگان Render:

- بعد از ۱۵ دقیقه بدون بازدید می‌خوابد؛ اولین بازدید بعدی حدود یک دقیقه طول می‌کشد. صفحه معرفی هنگام باز شدن، سرور را بیدار می‌کند تا وقتی بازدیدکننده دکمه را می‌زند آماده باشد.
- پردازنده ضعیف است؛ صفحه‌ها کمی کندتر از اجرای محلی باز می‌شوند.
- ۷۵۰ ساعت در ماه رایگان؛ برای یک سرویس کافی است.

## مرحله ۲: روشن کردن GitHub Pages

1. در مخزن گیت‌هاب: **Settings → Pages**.
2. در **Build and deployment** گزینه **Source** را روی **GitHub Actions** بگذارید.
3. به تب **Actions** بروید، workflow با نام **Pages** را باز کنید و **Run workflow** را بزنید (یا یک تغییر در `site/` push کنید).
4. بعد از حدود یک دقیقه صفحه در `https://kasrajo06-oss.github.io/nobatino-platform/` در دسترس است.

اگر آدرس نسخه زنده با `https://nobatino-demo.onrender.com` فرق دارد: **Settings → Secrets and variables → Actions → Variables → New repository variable** با نام `DEMO_URL` و مقدار آدرس Render بسازید و workflow را دوباره اجرا کنید.

workflow در [`.github/workflows/pages.yml`](../.github/workflows/pages.yml) است: محتوای `site/` و تصاویر `docs/images/` را کنار هم می‌گذارد، آدرس نسخه زنده را جایگزین می‌کند و منتشر می‌کند.

## نکات امنیتی نسخه نمایشی

- هر کسی می‌تواند با حساب‌های نمایشی، **از جمله اپراتور**، وارد شود و داده‌ها را تغییر دهد. این عمداً برای نمایش است و با راه‌اندازی دوباره پاک می‌شود.
- هیچ داده واقعی بیمار یا پزشک در نسخه نمایشی وارد نکنید. فایل‌های بارگذاری‌شده هم با راه‌اندازی دوباره پاک می‌شوند.
- `config.settings.demo` همیشه `STAGING` است و نمی‌توان با آن پیامک یا پرداخت واقعی گرفت. برای سایت واقعی از [`DEPLOY.md`](../DEPLOY.md) و سرور اختصاصی استفاده کنید.
- دسترسی از داخل ایران: `github.io` معمولاً باز است، ولی ممکن است دامنه‌های `onrender.com` برای بعضی کاربران فیلتر باشند یا Render ثبت‌نام از ایران را محدود کند. برای مخاطبان داخل ایران، نسخه اصلی روی سرور ایرانی ([`DEPLOY.md`](../DEPLOY.md)) راه مطمئن‌تری است.

## راه‌اندازی با Coolify (روی سرور خودتان)

[Coolify](https://coolify.io) یک پنل رایگان و متن‌باز شبیه Render است که **روی سرور خودتان** نصب می‌شود. Coolify خودش سرور نیست؛ اول یک سرور مجازی (VPS) لازم دارید. مزیتش این است که سرور نمی‌خوابد، محدودیت پلن رایگان ندارد و **دامنه لازم ندارد**: Coolify برای هر سرویس یک آدرس رایگان `sslip.io` می‌سازد.

### پیش‌نیاز

| | |
|---|---|
| سرور | Ubuntu 22.04 یا 24.04، حداقل ۲ هسته، ۲ گیگابایت رم، ۳۰ گیگابایت دیسک (خود Coolify هم حدود ۱ گیگابایت رم می‌گیرد) |
| شبکه | IP عمومی و پورت‌های 22، 80، 443 و 8000 باز |
| دامنه | لازم نیست |

سرورهای داخل ایران برای مخاطب ایرانی سریع‌ترند، ولی ممکن است نصب Coolify به‌خاطر دسترسی به `ghcr.io` و Docker Hub به میرور یا پروکسی نیاز داشته باشد.

### ۱. نصب Coolify (یک بار)

```bash
ssh root@SERVER_IP
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | sudo bash
```

بعد `http://SERVER_IP:8000` را باز کنید و حساب مدیر بسازید. این صفحه را سریع بعد از نصب باز کنید، چون اولین کسی که آن را باز کند مدیر می‌شود.

### ۲. اضافه کردن سایت

1. **Projects → Add** ← یک پروژه بسازید ← **+ New → Public Repository**.
2. آدرس مخزن: `https://github.com/kasrajo06-oss/nobatino-platform` ، شاخه `main`.
3. **Build Pack** را روی **Dockerfile** بگذارید و این مقادیر را وارد کنید:

| تنظیم | مقدار |
|---|---|
| Base Directory | `/` |
| Dockerfile Location | `/deploy/demo/Dockerfile` |
| Ports Exposes | `8080` |
| Domains | `https://nobatino.SERVER_IP.sslip.io` (به‌جای `SERVER_IP` آی‌پی سرور با نقطه) |

4. در **Environment Variables**:

| نام | مقدار | نوع |
|---|---|---|
| `DJANGO_SECRET_KEY` | یک رشته تصادفی طولانی | معمولی |
| `NEXT_PUBLIC_SITE_URL` | همان آدرس Domains | **Build Variable** |

5. **Deploy** را بزنید. ساخت اول حدود ۱۰ دقیقه طول می‌کشد. بعد سایت روی همان آدرس `sslip.io` باز می‌شود.

### HTTPS

ورود به سایت و تماس تصویری به **HTTPS** نیاز دارند. اگر آدرس در Domains با `https://` شروع شود، Coolify خودش گواهی Let's Encrypt می‌گیرد. اگر گرفتن گواهی برای `sslip.io` شکست خورد (گاهی به محدودیت Let's Encrypt می‌خورد):

- راه بهتر: یک دامنه یا زیردامنه رایگان به آی‌پی سرور وصل کنید و همان را در Domains بگذارید.
- راه موقت: آدرس را با `http://` بگذارید و متغیر `JWT_COOKIE_SECURE=false` را اضافه کنید. ورود و رزرو کار می‌کنند، ولی **تماس صوتی و تصویری بدون HTTPS کار نمی‌کند** (مرورگر به دوربین دسترسی نمی‌دهد).

### به‌روزرسانی

بعد از هر push در Coolify روی **Redeploy** بزنید. برای استقرار خودکار، مخزن را از **Sources → GitHub App** به Coolify وصل کنید.

### نسخه واقعی روی Coolify

آنچه اینجا راه افتاد **نسخه نمایشی** است (SQLite، داده ساختگی، کد ورود روی صفحه). فایل [`infra/docker-compose.prod.yml`](../infra/docker-compose.prod.yml) نسخه واقعی را با nginx و certbot خودش راه می‌اندازد که با پروکسی داخلی Coolify تداخل دارد. برای سایت واقعی فعلاً [`DEPLOY.md`](../DEPLOY.md) را دنبال کنید. اجرای نسخه واقعی روی Coolify به یک فایل compose جداگانه نیاز دارد.

## میزبان‌های جایگزین

image نسخه نمایشی به Render وابسته نیست و پورت را از متغیر `PORT` می‌خواند (پیش‌فرض ۸۰۸۰). روی هر سرویسی که Dockerfile اجرا کند کار می‌کند؛ کافی است مسیر Dockerfile را `deploy/demo/Dockerfile` و context را ریشه مخزن بدهید. حداقل منابع: ۵۱۲ مگابایت رم.
